Rules for the real rework

Everything we agreed on while making these mockups. The rules apply to the whole UI, not only to the screens shown here, and the list grows whenever we settle something new.

Principles

1One design language everywhere
Every screen, menu, panel and dialog in FancyMenu speaks the same design language: the same controls, surfaces, sizes, spacing, colors, type and motion, defined once and reused everywhere. Consistency across the whole UI matters more than any single screen looking special. When something new is needed, like a new kind of component, it's built from the parts that already exist and then added to the language, so the next screen reuses it instead of getting its own one-off look.
See: Controls & window chrome, Surfaces, and every rule below
2Everything fits and connects
Bars, gutters, lists and panels always fill the space they belong to and connect cleanly to the parts around them, like the text editor's line numbers running from the toolbar down to the status bar. Nothing ends with an odd gap or looks like it was just dropped in.
See: Text editor

Text and labels

3Never cut text off
No "..." dots anywhere: not to shorten a label, and not after labels that open a dialog. If a label doesn't fit, its container grows. The one exception is a value shown on the right of a menu row, like a long Text Content: it can't always fit, so it ends with … there, and opening the entry shows all of it.
See: Context menus, Menu bar
4Menus fit their longest label
Context menus and menu bar menus are always as wide as their longest full label, and resize right away when entries or labels change.
See: Context menus
5Labels next to their controls
A label sits on the same line as its control, macOS style, instead of above it or baked into a button.
See: Redesigned screens
6Help never repeats the label
Hover help explains what an entry does. It never shows the entry's name again.
See: Layout editor · Text element menu

Controls

7Cycle buttons are replaced
2 or 3 options become a segmented control. More options become a pop-up button with a chevron, or in menus a submenu with a checkmark on the current option.
See: Redesigned screens, Context menus
8On or off is a switch
Switches show the state at a glance, instead of colored Enabled and Disabled text.
See: Context menus
9Numbers with a range are sliders
A number with a fixed range, like a volume from 0 to 100% or an opacity, is a slider with its value right next to it, the same one context menus use, in menus, forms and windows alike. Dragging updates the setting live and counts as one undo step, not one per tiny move. Numbers without a range, like a time in milliseconds, are a number field with their unit and a stepper, like the HTTP request's timeout.
See: Context menus · today and proposed, Script editor · Play Audio's variables
10Steppers take steps that fit
Stepping by 1 is fine while a value stays between −10 and 10. Anything bigger takes far too many clicks that way, so a stepper steps by an amount that fits the value, like 5 seconds for a timeout or 100 ms for a time, and its buttons say the step on hover. When a value has a range, it gets a slider instead (rule 9), and steppers are only used where neither fits better.
See: Controls & window chrome, Edit HTTP Request, Script editor · today and proposed
11Scroll bars look the same everywhere
Everything in FancyMenu's own UI that scrolls, menus included, shows the same scroll bar as long as there's more to see: a round thumb 6 px wide with a 3 px inset and at least 28 px long, that grows to 8 px with a soft track on hover and gets darker while it's dragged. It never hides until you scroll, so a list that goes on always looks like one, and its colors come from the theme. Lists that show problems or find results put a mark for each into their scroll bar, or into the minimap where there is one. Elements in layouts keep their own Scroll Bar Style.
See: Controls & window chrome, Script editor · a long script and its minimap
12Colors show a swatch
Every color row shows a small swatch of the current color next to its hex value, so nobody opens the picker just to see it. Transparent colors show over a checkerboard. Colors whose default comes from the UI theme show that color and its hex like any other value.
See: Menu bar · layout editor (Window menu), Context menus · today and proposed, Color picker
13Every color format is editable
Hex, RGBA and HSV can all be typed into, and changing one updates the others right away. Hex takes #RGB, #RGBA, #RRGGBB, #RRGGBBAA and color names. Text that isn't valid yet stays in its field, marked red, instead of being replaced while you type.
See: Color picker
14Files show what they are
Rows that point to a file show its name with a thumbnail for images and videos or a play button for sounds, and None or Mixed like other values. Hovering shows a preview card with the full path, wrapped and never cut, plus the source and details. Missing files are flagged in red. Sources can contain placeholders: the row then shows the resolved file in a chip with { } tinted, and a placeholder that only resolves in game says so instead of looking like an error.
See: Context menus (Image element menu, file entries spec)
15Special cases look normal
When an entry works differently under the hood, it still looks and behaves like every other entry of its kind. A color that falls back to the UI theme shows that color, its hex and the usual reset arrow, not a special "Default" state, and it keeps showing its normal color while Invert Background Colors is on.
See: Menu bar · layout editor (Window menu)
16Placeholder support stays everywhere
Every setting that takes placeholders keeps it: the { } button switches to placeholder text, and a chip shows what it resolves to. This is also how booleans keep their third Manual state.
See: Layout editor · Text element menu
17Mixed selections are visible
When the selected elements disagree, the switch knob sits in the middle and values say Mixed.
See: Context menus · today and proposed
18Rows show their current value
Menu rows show their value on the right, so nobody opens a dialog just to check it. A reset arrow shows up on hover when the value isn't the default. Every row shows its state, not only the exceptions: On as well as Off.
See: Context menus

Menus

19Submenus forgive diagonal moves
While the pointer heads toward an open submenu, crossing other rows doesn't switch or close it for 350 ms. Entering the submenu cancels the switch, stopping on a row applies it after the grace time, and moving straight up or down switches instantly.
See: Menu bar, Layout editor · background menu
20Sections and separators match
Named sections use a centered label with a line on each side. Plain separators use the same light line, and both have exactly 12 px of space above and below.
See: Context menus
21Every menu is searchable
Typing in any menu or submenu searches it. The text goes to the menu under the pointer; with the pointer outside the menus, to the last menu you searched in, otherwise the main menu. While navigating with the arrow keys, it goes to the menu you are navigating. Matches are highlighted, section headers stay with their matches, and the menu keeps its width while you type.
See: Context menus · today and proposed, Menu bar
22Long menus show the search field
Menus with more than 10 entries show the search field from the start. Shorter menus keep it hidden until you start typing or press Ctrl+F, which also hides it again.
See: Context menus, Menu bar
23Growing lists collapse
Lists that can grow, like a screen's layouts, sit right in the menu while they are short (5 entries or fewer). Longer ones collapse into one row that shows the count and opens a searchable submenu.
See: Menu bar · customization overlay with 52 layouts
24Destructive actions go last
Delete, Kill-Switch and similar actions are the last row of their menu, in red.
See: Context menus, Menu bar
25Menu titles switch on hover
While a menu bar menu is open, moving to another title opens that menu without another click.
See: Menu bar

Windows and layout

26macOS window chrome
Traffic lights sit top left, and their symbols appear on all three at once when hovering the group. The window icon and title are centered.
See: Redesigned screens, Editor panels
27Exact window and menu edges
Windows, editor panels, menus, popovers and tooltips use exactly the corner radius, outline, inner highlight and shadow from the Surfaces reference below, in both themes and both materials. FancyMenu draws these differently today, and they carry most of the macOS feel, so no surface invents its own edge or shadow.
See: Surfaces, below
28Same sizes and spacing everywhere
Buttons, fields, pop-up buttons and segmented controls are all 28 px tall with a 7 px radius, and their text uses the regular weight. Window content, footers included, is inset 22 px from the window edge, so the buttons line up with the groups above them. Sections are 18 px apart, a section label sits 6 px above its group, and a note 7 px below it. Small tags, like file types or Active, share one chip style.
See: Controls & window chrome, Surfaces
29Live edits say so
Windows that change something on screen while you edit it show the change right away and say what previews live. Cancel, closing the window and Esc put everything back; Done keeps it as one undo step.
See: Color picker
30Browsers share one layout
Every file, folder and resource browser uses the same window: Back, Forward and Up, a Places button, a clickable path and search on top, a list with thumbnails, the shared preview on the right. The Places menu lists drives (only when the browser may leave the game folder), recent folders shared by all browsers, and common places.
See: File browsers
31Main buttons say what they do
Confirm buttons are named after the action, like Choose, Save, Replace or Use This Folder, instead of OK or Done. A destructive action, like replacing a file, turns the button red.
See: File browsers, Color picker
32Core actions are easy to find
The main actions of a screen, like New and Import in Profiles, are clear, prominent buttons, never small icons in a corner.
See: Profiles
33No space wasters
No headers or decorations that only repeat what is already visible, like an element-name header on top of an element menu. Simple lists beat crowded category grids.
See: Context menus

Motion

34Icons stay still
Icons don't play animations on their own. Today, menu icons wiggle and submenu arrows spin whenever the pointer touches them, and all of that goes. An icon can still animate later where the motion is actually needed, but nothing moves just for decoration.
See: Context menus, Menu bar
35Menus grow in quickly
Top-level menus keep today's grow-in when they open, just as quick: 120 ms from 78 % size with an ease-out, starting from the corner they open from. Submenus open instantly. The animation never holds up a click or a key press, and it's skipped entirely when UI Animations is off or the UI theme doesn't allow animations.
See: Context menus, Menu bar
36Scrolling is smooth
Everything that scrolls, like context menus, lists, text editors and windows, glides to where you scroll instead of jumping a whole step at a time. Another wheel turn while it's still moving just moves the target further, so scrolling never waits for an animation, and content that loads while scrolling never makes the view jump. It has its own setting, Smooth Scrolling, next to UI Animations and on by default, because most people still want smooth scrolling with UI animations off. With it off, the UI scrolls in instant steps like today.
Requested in Keksuccino/FancyMenu#1839

Under the hood

37Only old layouts have to keep working
The rework may change any code and API without keeping the old one around. Addons are allowed to break and need an update, so there are no compatibility layers or deprecated leftovers for them. The one thing that always keeps working is layouts made with older FancyMenu versions. The rework is mostly UI and backend and doesn't change what gets saved in layout files, so they load as they are. Where something saved does change, FancyMenu reads the old form and converts it on load.
Applies to every rule in Under the hood and Fix during the rework
38Placeholders say where they work
Every placeholder says where it works, through a new method that returns one or more places from an enum, like everywhere, in a world or while a world loads. The UI uses it to explain why a value is empty right now, like the "in game" chip on file entries, and to show where each placeholder works in the placeholder list.
Full plan: Keksuccino/FancyMenu#1850
39Get Variable gets a shorter name
The display name of the Get Variable placeholder (fancymenu.placeholders.get_variable) changes from "Get Variable Value (FM Variable)" to "Get Variable" in every language file, so its chip stays short in the text editor. The identifier getvariable stays the same, so existing layouts keep working.
See: Text editor
40Placeholder variables get types
Placeholder variables are all plain strings today. Each variable gets an optional type from a new enum, like on/off, number, choice, element, file or server address. The editor then shows the right control for it, every variable gets parsed the same way, and nothing needs hint defaults anymore. Variables without a type stay plain text.
Full plan: Keksuccino/FancyMenu#1849
41Placeholder defaults are real values
A placeholder inserted from the list works right away. Hint defaults like slot_number or put_identifier_of_audio_element_here turn into real values, like the first fitting element of the layout, or stay empty when nothing fits. Variable types explain what goes into each variable, so the hints aren't needed anymore.
Full plan: Keksuccino/FancyMenu#1851

Fix during the rework

Bugs we found while making these mockups, and changes that come with the rework.

42Line-break markers stay out of saved text
One-line values save line breaks as %!n!% and the spaces after them as %!s!%. Those markers end up in saved layouts, value previews and copied text, and every place that uses such a value has to strip them again.
See: Text editor · today and proposed. Fixed by rule 57: Keksuccino/FancyMenu#1860
43Toast titles without markers
A line break typed into the title of a Show Toast action leaves %!n!% in the toast, because the title never gets the markers removed.
See: Text editor · today and proposed. Fixed by rule 57: Keksuccino/FancyMenu#1860
44HTTP bodies keep their line breaks
The body of a Send HTTP Request action is saved as a one-line value, so its line breaks get deleted: a JSON body loses all its formatting, and "a", a new line and "b" get sent as "ab".
See: Text editor · today and proposed. Fixed by rule 57: Keksuccino/FancyMenu#1860
45Write File can write \n
Write File saves line breaks as the text \n and turns them back into line breaks when it runs, so it can't write an actual backslash followed by n.
See: Text editor · today and proposed. Fixed by rule 57: Keksuccino/FancyMenu#1860
46Dragging scrolls up too
While dragging an entry in the action script editor, moving above the list never scrolls it up, because the check compares the pointer’s x position with the list’s top y position. Dragging close to the left edge of the window scrolls up instead, anywhere in the list.
See: Script editor · today and proposed. Bug report: Keksuccino/FancyMenu#1852
47Folders and comments move like other steps
Move Up and Move Down, and Shift+↑/↓, do nothing for folders and comments in the action script editor. The menu entries are active, but the entry stays where it is.
See: Script editor · today and proposed. Bug report: Keksuccino/FancyMenu#1853
48A While runs again after a timeout
A While loop that hits its 3 second timeout once is skipped on every later run until FancyMenu reloads, because its timeout flag is only reset by a run that finishes in time. A timeout only stops the run that hit it.
See: Script editor · today and proposed. Bug report: Keksuccino/FancyMenu#1854
49Added and dropped steps land in the same place
Adding a step to a selected block puts it at the end of the block, while dropping one on the block puts it at the start. Both put it right below the block header.
See: Script editor · today and proposed. Bug report: Keksuccino/FancyMenu#1855
50Cancel only asks when something changed
The action script editor asks whether to discard everything on Cancel and when its window closes, even when nothing changed. It only asks when there are changes to lose.
See: Script editor · today and proposed. Bug report: Keksuccino/FancyMenu#1856
51Requirements become Conditions
Everything the UI calls a requirement is called a condition, all over FancyMenu: Loading Requirements becomes Loading Conditions, Manage Requirements becomes Manage Conditions, requirement groups become condition groups, and Requirement Caching becomes Condition Caching. The condition editor goes along, so texts like Edit Requirement Value, This requirement has no value and You need to edit the requirement value first! talk about the condition and its variables instead (rule 54). That's about 140 texts in en_us.json, plus the same ones in every other language file. The conditions themselves keep their names, like Is Singleplayer. Saved identifiers keep "requirement", so old layouts keep loading. Class names and the API can be renamed along with it, since addons are allowed to break (rule 37).
See: Script editor · today and proposed, where If and While already talk about conditions
52Action variables get types
Every action takes one string today, so many of them pack several settings into one text, like intro_seen:true for Set Variable or url|||POST|||{…} for Send HTTP Request. Each action can split it into variables, each with a type from the same enum as placeholder variables, plus a short summary for its row in the script editor. Set Variable gets Variable and New value, Play Audio gets Sound, Volume and Channel. The editor then shows the right control for every variable, the same way as for placeholders. Actions that don't declare variables keep one text variable with the raw value, and saved values stay as they are.
See: Script editor · today and proposed. Variable types: Keksuccino/FancyMenu#1849
53Everything describes and registers itself the same way
Placeholders, actions, conditions and listeners all get a display name, a description and a category from one shared list, plus a display name, description, type, default and example for every variable. Listener Variables get all of that except a display name, because people type them as $$key_name and the UI shows exactly that. Their texts are plain localized strings found by a key convention, instead of Components with formatting codes, so the UI can search, sort and style them itself. All four share one registry base with the same registration rules, and the same job gets the same method name in every kind, like one method for whether an entry shows in the editor.
Full plan: Keksuccino/FancyMenu#1857
54Values become variables
What placeholders, actions and conditions take as input is called a variable, not a value, everywhere. In the editors, Edit Action Value, Configure Value, Value: and This action has no value talk about variables, and the same goes for conditions. Descriptions too, like the Required values:, Optional values: and Values: lists of placeholders, or Takes the key of an effect as value. Every language file follows. In the API, getValueNames, hasValue, hasRawValue, getValueDisplayName, getValuePreset, getValueFormattingRules and editValue make way for the variable definitions, and the values map of DeserializedPlaceholderString becomes the shared variables object. The placeholder string writes "vars" instead of "values" and still reads "values", so old layouts keep working. What listeners hand to their scripts are Listener Variables. A variable still has a value, so phrases like the value of a variable, or names like Is Variable Value and Possible Values: 0-100, stay.
See: Text editor, Script editor · today and proposed. Plans: Keksuccino/FancyMenu#1849, Keksuccino/FancyMenu#1857
55One clean system for $$ names
$$name reads something by its name: a Listener Variable like $$old_value, a FancyMenu variable like $$coins, or $$value, the current value of a Checkbox or Slider. That last one isn't a variable, so these are element values, and the UI names them after their element, like Checkbox value. In the code, ValuePlaceholderHolder, addValuePlaceholder, getValuePlaceholders, applyValuePlaceholders and the two separate "$$" constants drop the placeholder name and become one shared resolver for $$ names. Listeners and elements hand their names to the context a script or condition runs in, instead of copying them into every action, block and condition like today. Texts stop calling them placeholders, like the '$$value' placeholder in the Checkbox and Slider descriptions. At every $$ the longest matching name wins, so $$item_key never eats the start of $$item_key_count, and $$ works in every text, also in ones without a placeholder. Both go wrong today.
See: Script editor · today and proposed. Plan: Keksuccino/FancyMenu#1857. Bug reports: Keksuccino/FancyMenu#1858, Keksuccino/FancyMenu#1859
56New variables can't take $$ names
Wherever someone names a new FancyMenu variable, like Manage Variables, Set Variable, the linked variable of Checkbox, Slider and Input Field, or the response variable of Send HTTP Request, names that Listener Variables or element values use, like old_value, player_name or value, are refused, and the field says what uses the name. Old layouts, /fmvariable from a server and addons that add new listeners can still bring such a variable, so it keeps working: Get Variable reads it by name, Manage Variables marks it, and when both have the same name, $$ always picks the Listener Variable or element value, so $$old_value in a listener script always means the listener's variable.
Plan: Keksuccino/FancyMenu#1857
57Typed line breaks are stored one way
Every text property says whether it's one line or multi-line and holds real line breaks, and only the layout file escapes them, in one place. One-line values keep the line breaks and indentation people type, and FancyMenu joins them in one single place when the value gets used, instead of %!n!% and %!s!%. %n% and a typed \n stay text codes, because variables, placeholders and server data use them to make line breaks. Old layouts convert per property, the way each one uses its markers today, so the same text comes out. The Toast title and message, the Write File content and the HTTP body become multi-line, and old HTTP bodies keep sending as one line. This fixes rules 42 to 45.
See: Text editor · today and proposed. Plan: Keksuccino/FancyMenu#1860
58Steps can be turned off
Every step in the script editor gets a Runs switch, and Ctrl+/ turns the selected steps on or off. A step that's off stays where it is, dimmed with an Off chip, and the script skips it, like commented-out code. Turning off a block, like If, While, Folder or Delay, skips everything inside it. Turning off an If also skips its Else If and Else, while turning off a single Else If or Else only skips that branch. The layout saves one extra line for each step that's off, so old layouts load with everything on (rule 37).
See: Script editor · today and proposed
59Collapsing is view state
Collapsing a block in the script editor isn't an edit. It's still saved with the layout, so a script opens the way it was left, but Undo and Redo skip it, and it doesn't count as a change, so Cancel doesn't ask about it (rule 50). Every branch collapses on its own: collapsing an If only hides the If's own steps, and Else If and Else get their own collapse arrow and saved flag. In old layouts, a collapsed If opens collapsed, and its Else If and Else open expanded.
See: Script editor · today and proposed
60Variable actions get shorter names
The display names of Set Variable Value (FM Variable), Delete Variable (FM Variable), Clear All Variables (FM Variable) and the Is Variable Value (FM Variable) condition become Set Variable, Delete Variable, Clear All Variables and Is Variable Value in every language file, matching Get Variable (rule 39). Their identifiers stay the same, so layouts keep working.
See: Script editor · today and proposed

Context menus that show their state

The right-click menus are where most of FancyMenu gets configured, so they get the same controls as the windows: switches, segmented controls and values you can read at a glance. Every menu can be searched by typing, long menus get sections and show their search field right away, the most-used actions move to the top, and placeholder input works in every row that supports it.

Search
Every menu and submenu can be searched: just start typing. The text goes to the menu under the pointer, otherwise to the last menu you searched in, otherwise the main menu. Short menus keep the field hidden until you type or press Ctrl+F. Matches are highlighted, section headers stay with their matches, and the menu keeps its width while you type.

Long menus
Menus with more than 10 entries show the search field from the start, so filtering is never a hidden feature where it matters most. Each element type's own settings come first. The shared ones (position, visibility, effects) move into three submenus.

Changes beyond the UI All approved

These menus need more from every setting than FancyMenu knows today, so each one is a rework rule. Plan: Keksuccino/FancyMenu#1863.

Every setting describes itself Approved, rule 79
The value on the row, the reset arrow, Mixed, switches, sliders, swatches, the help card and grayed-out rows all come from the setting: its value, default, type, choices, range, unit, step, help, section and the setting it depends on. Today many entries are built by hand and know none of that.
Element types bring their own icon Approved, rule 80
New Element shows an icon for each type, and the Layers panel and element pickers use the same one. Today every type has the same icon.

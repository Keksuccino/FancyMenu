Variables you can watch, find and trust

The Variables window shows every value live, where each variable is used and what changed it last. New variables get their name, value and reset behavior in one sheet, and renaming or deleting is safe, because the window knows every place that uses a name.

What gets in the way
  • Values sit in brackets after the name, in warning orange, and long ones like an HTTP answer run off the row.
  • Everything happens in a right-click menu, and only the hint in an empty list mentions it. Adding asks for the name in one window, and the value needs a second one.
  • The list doesn't change while it's open, so a variable that a ticker counts up keeps showing its old value.
  • Nothing says where a variable is used. Deleting one that a layout needs breaks it without a word, and there's no rename at all, only copy, paste and delete.
  • Clearing on game launch is a cycle row in the right-click menu, the list doesn't show which variables do it, and they can only go back to empty, not to 0 or false.
  • Nothing shows what changed a variable, so a script that sets the wrong value means guessing.
  • Copy and Paste only make a copy of a variable inside this window, while $$coins, the thing a text needs, has to be typed by hand.
  • Variables from old layouts that $$ reads differently now, like old_value in a listener script, look like any other variable.

The window, piece by piece

The list
Each row shows the name in monospace and the value below it. Empty values say empty, and values that are too long end with … there, while the details show all of it. A value that changes gets a short blue highlight, so tickers and listeners are easy to watch. A small arrow marks variables that reset when the game starts, and a warning marks names that $$ reads differently. Shift- and Ctrl-click select several, and the search highlights what it found in names and values. When nothing matches, the list offers to create a variable with that name.
The value
A field that grows with the value, up to eight lines, then scrolls. Enter saves and Shift+Enter starts a new line, Esc takes your typing back, and clicking somewhere else saves too. The value isn't saved while you type, so a listener for the Variable Updated event runs once per change instead of once per letter. If the game changes the value while you type, the note says what it changed to, and Enter replaces it. The button in the field opens the text editor for long values.
When the game starts
Keep value or Reset. Reset shows the value to go back to, empty by default, and Reset Now sets it right away, which helps while testing. The note says it in one sentence, like Every time Minecraft starts, the variable goes back to false. With several variables selected, a mixed choice shows no selection and the note names which ones reset.
Used in
Grouped by where: layouts, a custom GUI's own settings like its screen title, global customizations, FancyMenu's settings like the game intro source, listeners, schedulers, and the values and reset values of other variables. Each layout says which screen it's for, like the title screen or the Coin Shop custom GUI, or that it's universal, with the screens it's limited to when it has a list. Below each come the elements or scripts and what they do with the variable, like Click script · Set Variable, Text · $$coins or Shader code · fmVarInt_quest_stage. The open button on hover jumps there, or selects the other variable. Text loaded from files, web addresses or HTTP answers can't be checked, and a note under the list says so. Nothing used yet? It says how to use it, with its $$ name.
Recent changes
Time, old value → new value, and what made the change: a Set Variable step and the element whose script ran, a slider or input field, an HTTP request, a /fmvariable command from the server, the reset when the game started, or you. The last three show, the rest one click away. Repeated changes from the same source become one row with a count, so a ticker doesn't flood it. It covers the time since the game started and isn't saved.
The footer
Changes apply right away, so the menus behind the window show them, and the note says so (rule 38). Done closes the window. Cancel and the red light take back only what was changed in this window: values that the game changed meanwhile, like a ticker's, stay. After a delete or a rename, the note turns into what happened with an Undo link.

New, rename, delete

New Variable
1New Variable, Ctrl+N, or the offer in an empty search adds the variable right away and selects it, with its name ready to type over.
2Capitals turn small and spaces turn into _, and characters that don't work can't be typed.
3Taken names are refused right there: an existing variable gets a Show It link, and names that Event Variables or element values use say what uses them (rule 74).
4Enter keeps the name, Esc keeps new_variable. The value and what happens when the game starts are set in the details.
Rename
1F2 or the pencil next to the name turns the name into a field, checked the same way as a new name.
2Nothing uses it? Enter renames it right away.
3Something uses it? A sheet says how many places in which layouts, listeners and schedulers, and offers Rename and Update 4 Places, Only Rename or Cancel.
4It also warns that it can't change text loaded from files, web addresses or HTTP answers, or /fmvariable commands on servers.
Delete
1The delete button in the details or the Delete key, for one variable or several.
2Nothing uses them? They're gone right away, and the footer offers Undo.
3Something uses them? A sheet says where and what happens: texts that show them go empty, and conditions that check them stop matching. Delete is red.
4Undo brings them back until you press Save.

Special cases it handles

  • Set Variable and /fmvariable can create names that the name field wouldn't allow, like capitals or spaces. They show as they are, work as they are, and Rename offers the cleaned-up name.
  • Variables that a server creates or changes with /fmvariable while the window is open show up live, with the server as the source in Recent changes.
  • Values with line breaks show their first line in the list and every line in the field.
  • A variable named like an Event Variable or element value, like old_value from an old layout, keeps working: the details explain that $$ picks the other one in those scripts and Get Variable still reads this one, with Rename It right there.
  • Duplicating a variable names the copy coins_copy, then coins_copy_2. Today's Paste makes coins_Copy, with a capital the name field doesn't even allow.
  • Undo and Cancel never take back changes that the game made meanwhile, only the ones made in this window.
  • Usage covers every place that takes a variable name, also the ones in disabled layouts, so a variable isn't marked as unused just because its layout is off.
  • Filters show as a chip under the search field, so a shorter list is never a mystery. The chip's × shows everything again.

Changes beyond the UI All approved

The window above already uses these. They change how variables get saved or tracked, so each one is a rework rule.

Variables know where they're used Approved, rule 87
An index of every place that uses a variable name: layouts (universal and disabled ones too), a custom GUI's own settings, global customizations, FancyMenu's settings, listeners, schedulers, and the values and reset values of other variables. Custom GUIs use ordinary layouts, so theirs count as layouts like any other. It reads the variable definitions of Keksuccino/FancyMenu#1849, where every variable that takes a variable name has the lookup fancymenu:variables, so actions, conditions, placeholders and element settings from addons count too. On top of that come $$ names in texts and the fmVar…_name uniforms in shader code. It's built in the background when the window opens and refreshed per file that changed. Used in, the Not Used filter, rename and the delete warning all read it. Text that gets loaded when it's used, from a file, a web address or an HTTP answer, can't be indexed, because it can change any time.
Renaming updates every place Approved, rule 88
With the same index, a rename changes the name in every place that uses it, other variables' values included, and saves those places through their normal save path, as one undo step in this window. $$ names only change where the whole name matches, so renaming coins never touches $$coins_record. Text loaded from files, web addresses or HTTP answers, and a server's /fmvariable commands, can't be changed, and the rename sheet warns about that.
Variables reset to a value Approved, rule 89
Next to reset_on_launch, each variable saves the value it goes back to when the game starts. Variables from older versions don't have one, so they go back to empty, like today. This only changes the variables file, not layouts.
Changes remember who made them Approved, rule 90
Setting a variable passes where the change comes from: the script and its owner (rule 81), the element, the HTTP request, the server command, the reset on game start or this window. FancyMenu keeps the last 20 changes per variable in memory for Recent changes. Nothing of it gets saved.
Previews of long values end with … Approved, rule 10
Rule 10 now says it outright: labels never get cut, but a preview of a long value, like a variable's value under its name in the list, ends with … where it runs out of room, because it can be a whole HTTP answer. Selecting the variable shows all of it.

A text editor that speaks placeholders

The editor works like the text editors people already know: find and replace, word wrap, undo by word, Tab to indent. Placeholders turn into chips you can read and edit like a form, suggestions show up as soon as you type {, and every placeholder tells you what it shows right now. The editor also adapts to what you edit: Markdown text, one-line values or shader code.

What gets in the way today
  • Placeholders are raw JSON like {"placeholder":"getvariable","values":{"name":"coins"}}. One missing quote breaks them, and nothing points it out.
  • The placeholder list only pastes the default code. Every value still gets edited by hand inside the JSON.
  • There's no way to see what a placeholder shows right now.
  • There is no find and replace and no word wrap, so long values run off to the right.
  • In one-line values, line breaks and the spaces after them quietly disappear when the value is used, so "Hello", a new line and "world" turn into "Helloworld". A red "single line" label is the only hint.
  • Undo goes back one character at a time.
  • Tab doesn't indent, and Enter doesn't keep the indentation of the line above.

Chips and Code show the same text

The switch in the toolbar only changes how placeholders look. Clicking a chip opens its variables as a form: on and off variables get a switch, variable names get a pop-up list of your variables, and every variable has a { } button for placeholders inside it. A chip moves and deletes as one piece, so a placeholder can't end up half deleted.

One-line values

Many values are used as a single line, but they can get long. The editor still lets you split them up, marks every continued line with ↳, and explains in the status bar what happens: line breaks and the spaces at the start of the next line are left out. Inside a placeholder that's always safe, because FancyMenu ignores spaces between its parts.

Special cases it keeps handling

  • Some fields only accept certain text: labels can't be empty, tooltips can't be only spaces, and numbers typed as text must be numbers. Done stays disabled and says why right next to it.
  • Action and condition values open with their preset when they're empty, and an empty Delay falls back to its default.
  • The profile description has a maximum length. The status bar shows how much is left when it gets close.
  • FancyMenu doesn't look for placeholders in text with 17,000 characters or more. The status bar warns before you get there.
  • $$name is a short way to show a variable. The editor colors it and suggests variables after $$.
  • Placeholders can sit inside the variables of other placeholders. Chips show them as smaller chips, and the Code view keeps them on one line.
  • Where placeholders don't work, like shader code or the profile description, the Chips and Code switch and the sidebar are hidden.
  • With text selected, the formatting buttons apply to the selection. Markdown wraps it, like **selected**, and pressing the same button again takes the markers off. Formatting codes go in front of it, with &r after it plus the codes that were active before, so the rest keeps its look. Alignment, headings, quotes, lists and code blocks apply to every selected line, and the status bar shows how much is selected.
  • Only the Text and Tooltip elements render Markdown. Everywhere else, the formatting buttons write formatting codes instead, and Markdown-only tools like alignment, inline code, the Insert menu and hex colors are hidden.
  • FancyMenu's own Markdown codes all have a place in the toolbar or the Insert menu: ^^^ and ||| alignment blocks, %#RRGGBB% colors, %!!font% fonts, ;; plain text, and [text](click:id) and [text](hover:id) markers for the Markdown Text Clicked and Markdown Text Hovered events. Alignment markers get a short hint in the text, so it's clear what they do.

One way to store typed line breaks Approved, rule 75

This changes how FancyMenu stores text, not only how the editor looks. Plan: Keksuccino/FancyMenu#1860.

Today: five ways to store a line break
%!n!% and %!s!%one-line values in the editor, removed again by compileSingleLineString wherever the value gets used%n%element sources, tooltips and item lore. It's also a text code: rendered text turns it into a line break, even when it comes from a variable or a placeholder\nCellScreen fields, Write File, Toast and the profile description. Rendered Markdown text also reads a typed \n as a line break%%!serialized_property_newline!%%saved properties$prop_line_break$the properties parser
  • The markers end up in saved layouts, value previews and copied text.
  • Every place that uses a one-line value has to remember to remove them. The Toast title doesn't, so a line break leaves %!n!% in the toast.
  • The HTTP request body is a one-line value, so its line breaks get deleted: a JSON body loses all formatting, and "a", a new line and "b" are sent as "ab".
  • Write File stores \n as text, so it can't write a real backslash followed by n.
  • The cache behind compileSingleLineString keeps every value it ever sees until the next reload.
Proposed
  • %n% and a typed \n stay text codes and keep working exactly like today. Variables, placeholder outputs, HTTP answers and files use them to make line breaks, so they are never converted or removed.
  • Only line breaks typed in the editor change: every text property says whether it's one line or multi-line, holds real line breaks, and the layout file escapes them in one place, the property serializer.
  • One-line values keep exactly the line breaks and indentation you type, so your formatting comes back the way you left it, without %!n!% and %!s!%. When the value gets used, FancyMenu joins the lines in one single place, like today: line breaks and the spaces at the start of the next line are left out. Nothing that uses a value has to remember that anymore, so a marker can't end up in a toast again. The joined text is kept with the value, instead of in a cache that grows until the next reload.
  • Old layouts: every property converts only the markers it used itself, the way it uses them today, so the same text comes out. There's no replace over everything, so a \n that's a JSON escape in an HTTP body, part of a regex or a Windows path stays as it is.
  • The Toast title and message and the Write File content become multi-line values. Old ones are converted the way they're used today, and Write File can then write a real backslash followed by n.
  • The HTTP body becomes multi-line too. Bodies from old layouts get a saved Send as one line setting that's on, so they send exactly what they sent before and keep their formatting in the editor.
Stays the same: what comes out in game for every existing layout, and how one-line values work in the editor.
